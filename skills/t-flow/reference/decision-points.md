# 用户决策

澄清完成确认目标与范围；PRD/spec-delta 完成后确认需求编号与范围（approve specify）；ADR 独立生成后确认决策（approve adr）；UI 原型生成后确认原型没有问题（无界面需求时用 skip ui <原因> 跳过该停顿点）；设计完成确认技术方案（小型变更——无架构调整、无数据迁移、无新接口——可 skip design 提出原因，等待用户确认后 approve skip-design <用户原文> 才能跳过）；归档前确认验收。只把实际用户确认原文写入 approve，不得代替用户批准。**各停顿点确认用交互式确认卡片**（宿主 agent 的选项问答工具，如 AskUserQuestion）请用户点选「确认 / 需要修改」，不要求用户回复文字；只把用户实际点选的选项文字作为确认原文写入 approve，不得代用户点选或伪造确认；不支持卡片的环境回退文字确认，同样记录原文。已确认且输入未变直接复用；缺事实自行调查，缺业务决定再问。安装依赖已获授权，不逐个询问。UI Skill 内必要业务决定沿用现有明确确认，不默认为已批准。

停顿点由 protocol 各节点的 approval 字段声明（yt.mjs 由此推导门禁节点），增删或调整停顿点会改变 protocolHash，进行中变更需 migrate。design 的确认指纹覆盖 specify 全部产物，PRD/ADR/spec-delta 变化会使 design 确认自动失效；specify 自身也有确认，故范围契约在 PRD 阶段即被用户确认一次。

验证-修复循环超限时，向用户展示失败历史并用卡片让其点选方向（继续修复/调整需求/停止），把点选文字用 decide 记录后解除。

UI 默认主 Skill，用户已有偏好优先；工具选择不新增停顿，原型确认保留。轻量模式只有 specify/archive 两次确认。完整模式每份澄清、PRD、ADR、UI、Design 完成后分别展示并停止等待用户确认，确认后才生成下一阶段产物；禁止合并确认。
