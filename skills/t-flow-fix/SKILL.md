# t-flow-fix

用于已有 change 的小范围缺陷修复。直接定位、修改、验证和更新文档，不加载标准节点 Skill，不推进工作流状态机。

### 命令与目标

推荐始终显式指定 change：

```text
/t-flow-fix <change-id> <问题描述>
```

省略 change-id 时：

```text
/t-flow-fix <问题描述>
```

仅在当前 active 指向明确的未归档 change，或项目中只有一个未归档 change 时继续。多个候选且目标不明确时先列出候选并请用户指定，禁止猜测。没有对应 change 时如实说明，不自动 `init`，不修改 `docs/t-flow/archive/` 中的历史。

### 适用边界

- 适用于不改变已确认需求范围的小缺陷、错误处理、兼容性和局部回归修复。
- 修复导致新增或删除 AC、改变权限规则、页面契约、接口契约或数据迁移方案时，先向用户说明范围变化，不得借快速修复擅自改写已确认需求。
- 不执行 `init`、`approve`、`advance`、`reopen`、`skip`、`migrate`、`task`、`archive` 等状态推进命令。
- 不直接编辑 `.t-flow/runs/`、审批记录、`evidence/` 或执行日志，不伪造标准工作流证据。

### 步骤

1. **读取上下文**  
   确认 `docs/t-flow/change/<change-id>/` 存在，读取与问题相关的 PRD、设计、计划、测试报告和项目约束。状态文件只可作为只读上下文，不作为快速修复的推进依据。

2. **复现并最小修复**  
   先用现有测试、日志或实际调用确认问题与根因，再修改最小必要文件。遵守目标项目现有代码与测试约定，不顺手重构无关模块。

3. **直接验证**  
   运行与修复直接相关的真实测试或调用，记录实际命令、退出结果和关键断言；再按影响范围运行必要回归。这里不使用 `yt.mjs run` 生成标准工作流证据。只执行了局部测试时不得宣称全量回归通过，未执行项明确写 `not_run`。

4. **更新对应 change 文档**  
   修复和验证完成后，始终向 `docs/t-flow/change/<change-id>/fix-log.md` 追加一条记录，不覆盖历史。没有该文件时按本 Skill 的 `templates/fix-log.md` 创建。每条记录包含：
   - 时间、change-id、问题与根因；
   - 修改文件和行为变化；
   - 实际验证命令、结果及未测项；
   - 同步更新的文档和遗留问题。

   同步更新受修复影响且已经存在的 `prd.md`、`spec-delta.md`、`design.md`、`plan.md` 或 `test-report.md`，使文档与真实行为一致；无影响的文档不改。不得为表示通过而手工改写 `test-results.json`、任务证据或审批状态。直接更新已确认产物可能使标准工作流指纹失效，不得隐瞒；后续恢复标准工作流时应先运行 `doctor`/`check` 并按检查结果重新确认和验证。

5. **汇报结果**  
   简要说明根因、修改文件、实际测试、`fix-log.md` 和其他同步文档、未测项。除非用户另行明确要求，不自动提交、推送、部署或归档。

### Red flags

| 想法 | 风险 |
|---|---|
| 用户只说“修复”就自动启用本 Skill | 本命令仅在用户明确声明时使用 |
| 多个 change 任选一个 | 会修改错误文档，必须明确 change-id |
| 快速修复顺便 approve/advance | 会绕过标准门禁，本命令禁止推进状态 |
| 测试没跑就写修复完成 | 文档必须记录真实结果和 not_run |
| 只改代码不更新 change | 每次完成必须追加 fix-log.md，并同步受影响文档 |
| 手工改 evidence 或 test-results 表示通过 | 属于伪造状态与证据，禁止 |
| 修改归档历史 | 归档是历史记录，本命令只处理未归档 change |
