# t-flow-fix

用于已有未归档 change 的小范围缺陷修复，不推进工作流状态机，不改变任务状态或用户审批。不加载标准节点 Skill。

## 目标与边界

`/t-flow-fix <change-id> <问题描述>`；省略 id 时，仅在当前 active 明确或只有一个未归档 change 时继续。多个候选且目标不明先列出候选请用户指定。没有 change 不自动 init，不修改 `docs/t-flow/archive/` 中的历史。

只处理已进入 execute、verify 或 archive 的变更；前期节点继续当前阶段。读取相关 PRD、ADR、设计、计划、任务与结果，以及目标项目约束。使用 `context` 定位，只有异常才 doctor，不重复加载完整流程。

仅修复已确认行为内的小缺陷。新增/删除 AC，或改变权限、页面/接口契约、数据迁移方案时，立即停止快速修复，向用户说明范围变化，回到对应阶段重新确认；不得先改需求或设计再补确认。澄清、PRD、ADR、UI、Design 仍须分别确认，跳过 Design 也须用户确认。

## 修复与验证

1. 用现有测试或实际调用复现问题，定位根因与受影响任务，选择最小回归。普通 Shell 可作只读调查，不在持锁前修改实现。
2. 将最小补丁写成项目内临时 Bash 修复脚本（放项目工具目录，不放 change 目录）。脚本须检查预期旧内容或使用带上下文的补丁，不能盲目覆盖文件。脚本只修改本次实现和相关测试，不修改 change 文档、工作流状态或审批。
3. 从项目根执行：

```sh
node <t-flow>/scripts/yt.mjs --change <id> fix <任务id> \
  --repair <修复脚本相对路径> --input <相关测试或配置> \
  --expect <通过条件> --reject <失败条件> -- <真实测试命令>
```

`fix` 在同一 change 锁内执行修复脚本和真实测试，共用 run 的超时、断言、凭证扫描及输入指纹。只重新验证已经改好的代码时可省略 --repair。不要在 Shell 先改源码再登记，避免绕过锁。

每次覆盖保存最新结果到现有 state.json，不生成 logs/、evidence/、attempts/ 或 fix-log.md。失败/超时/中断阻断验收，失败片段仅在终端显示。修复期间禁止标准流程的写入操作，反向也一样；归档恢复中禁止修复。

任务的完整 acceptance 是本次验证范围，必须真实覆盖；--input 包括相关测试与配置。同一次真实测试可刷新该任务与已有关联套件的结果，无关结果不动。未覆盖的任务/套件仍须补测，不能扩大通过结论。测试脚本修改必须参与指纹，不能执行后删除绑定输入。

## 结果与恢复

运行器只更新已有的受影响测试结果；verify/archive 阶段同步已有 test-report.md 为结果表，包含状态与失败或未测原因，不记录命令、日志或证据。execute 阶段不提前创建或更新后续测试报告。

不追加 fix-log.md，不新增修复报告。历史 fix-log.md 保留但不再追加。临时修复脚本不属于验证输入时执行后可清理；测试本身保留在项目测试目录。

不直接编辑 `.t-flow/runs/` 或手工补写通过结果。运行器不推进 currentNode、不改 completedNodes、任务状态或审批原文。代码变化后的旧交付验收会失效，后续标准流程须重新取得用户确认；不为复用测试而伪造批准。

修复脚本若改写 change 文档或状态，运行器拒绝成功登记并保留失败，不自动恢复 change 文档，阶段与审批仍保留原值。先核对改动；契约确需变化则回到对应阶段确认。不得绕过门禁手工修正状态 hash。

最终回复简短说明根因、行为变化、实际测试结果、未测项及是否需重新确认。除非用户另行明确要求，不提交、推送、部署或归档。
