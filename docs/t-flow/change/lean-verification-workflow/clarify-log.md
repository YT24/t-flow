# 需求澄清：精简验证工作流

## 用户输入与已确认意图

- 用户认为测试时间比开发时间多好几倍，希望简化测试。
- 后端以单元测试通过、数据正确为主要验收依据。
- 前端采用构建检查、少量组件测试、1 条核心 E2E 和少量人工冒烟。
- 用户要求继续优化并修改工作流，减少重复验证与不必要的浏览器组合测试。

## 目标与范围

建立默认的精简验证策略，并同步到需求、设计、验证说明和模板：

1. PRD 只把用户可观察、需要交付门禁的结果定义为必测 AC；内部排列组合、普通异常分支和实现边界优先由自动化测试集覆盖，不全部升级为独立验收门禁。
2. 同一行为只在一个最合适的层级验证。一个真实执行的用例可以通过 `acceptance` 数组覆盖多条相关 AC，避免为每条 AC 重复启动相同环境或浏览器。
3. 后端纯逻辑使用单元测试；涉及持久化时以最终数据、约束、事务或审计记录正确作为验收依据，不要求通过前端重复验证所有后端规则。
4. 前端默认采用构建/静态检查、少量共享组件测试、1 条核心链路 E2E 和必要的少量人工冒烟。无界面变更不要求 E2E。
5. 浏览器只验证代表性用户链路和前端自身交互，不重复执行全部角色、业务对象、规则和后端异常组合。
6. 测试报告按实际测试套件组织，并建立套件到 AC 的映射；保留逐 AC 状态、真实证据和未测项，不用汇总通过数掩盖未测验收项。

## 不做事项

- 不取消 PRD/设计/验收等用户确认门禁。
- 不取消所有已确认 AC 必须有通过证据的要求，也不把 `not_run` 自动视为通过。
- 不删除证据输入绑定、日志、runId、输入变化后重新验证等防伪和防过期机制。
- 不要求所有项目使用同一种测试框架，也不引入新的测试依赖。
- 不自动修改历史变更的验收标准；变更既有 AC 或验证方式仍需回到对应阶段重新确认。

## 角色与权限

- 用户：确认需求范围、验收标准及任何降低或改变既有验收方式的决定。
- 执行 agent：根据变更影响选择最低有效验证层级，合并重复场景，如实记录证据和未测项。
- 工作流运行器：继续校验 AC 覆盖、必测状态和证据有效性，不负责判断测试语义强弱。

## 验收条件

- AC-01-1：需求与设计指导不再把内部场景排列组合默认展开成大量独立必测 AC，并要求优先共享测试套件覆盖相关 AC。
- AC-01-2：验证指导明确后端以单元测试和数据正确性为主，前端默认只需构建、少量组件测试、至多 1 条核心 E2E 与必要人工冒烟。
- AC-01-3：验证指导明确禁止在浏览器中重复验证已由后端覆盖的角色、对象和规则全组合，同时保留真实权限、数据或界面行为被声明为 AC 时的有效验证。
- AC-01-4：模板与 README 说明一次测试可映射多条 AC，且仍须逐条记录状态、证据和未测项。
- AC-01-5：现有状态机、确认门禁、证据完整性和历史变更兼容行为保持不变，项目回归测试通过。
