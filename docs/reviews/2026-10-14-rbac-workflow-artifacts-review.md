# RBAC 旧版文档产物审查与 t-flow 优化

报告日期：2026-10-14。前一轮已读取的历史样本位置：`/Users/yangte/Documents/IdeaProjects/sy-com-link/docs/t-flow/current/`，change-id 为 `rbac-management`。

结论：这些产物对目标、分层、兼容性和实现计划描述较完整，但“全部验收条件达成”的结论超出了已记录的验证范围。最重要的改进是从需求分组追踪到每条验收标准，区分证据层级，并核对跨阶段范围与授权契约。

前一轮采样读取了澄清、PRD、ADR、增量 Spec、UI、设计、计划、任务、测试与归档报告，以及需求用例证据、相关日志摘要和运行状态。没有复测业务接口、数据库或浏览器行为；以下权限问题是文档中的设计缺口与风险，不代表已确认业务代码存在漏洞。本轮仅修改 t-flow，未改写业务项目产物。2026-10-14 收尾时，原样本目录在当前环境中已不可见，未在相邻项目目录找到该原型；以下来源采用采样时的文件名和行号，运行状态也仅代表当时记录，不能据此判断业务项目现在的状态。

## 1. 采样时的产物与运行状态

- PRD 有 8 个 REQ、43 个明确的 `AC-NN-N` 验收编号。
- test-results.json 有 8 个需求级用例，全部登记 passed，没有逐 AC 的覆盖字段。
- tasks.json 有 9 个任务，全部登记 done；其中 T9 的验收条件包含尚待执行的同 token 权限回收验证。
- 磁盘状态在 archive 节点，clarify/specify/ui/design 有确认记录，archive 尚无确认。这是归档待验收，不能把归档报告存在等同于已归档。

## 2. 优先修复的问题

### P1：需求覆盖掩盖了未测验收标准

证据：PRD 的同 token 验收条件（历史来源：`prd.md:143`）、未执行的手工验收（历史来源：`test-report.md:51`）、归档结论（历史来源：`archive-report.md:54`）。

AC-06-4 要求授予权限后成功调用，再回收权限，用同一个 token 验证拒绝。报告将此项、真实菜单与按钮走查、Liquibase 首次建表留待部署后执行，却同时宣称满足推进条件、全部验收达成。一个 REQ 内还有多项 AC，只登记 REQ passed 无法暴露这些缺口。

优化：每个用例记录完整 `acceptance` 编号数组、验证方式及证据；全部已确认 AC 都必须有已通过的必测用例。未执行的手工项保持 not_run。改变验收范围或方式需回退更新需求并重新确认，不能自动改为可选。

注意：43 条 AC 缺少显式映射不等于 43 条全部失败；现有记录不足以给出准确的逐 AC 已通过数量。

### P1：验证命令可能吞掉失败，成功标记与断言过弱

证据：回归命令与断言（历史来源：`evidence/REQ-08-regression.json`）、前端静态检查（历史来源：`evidence/REQ-07-frontend-perm.json`）、种子检查（历史来源：`evidence/REQ-02-seed-data.json`）。

- Maven 输出经 grep、前端构建经 tail 过滤，再 echo 成功标记；未传播管道失败时，工具错误可能被包装成退出码 0。
- 回归的 `Tests run: 58, Failures: 0|BUILD SUCCESS|built in` 是任一匹配，不代表三个条件全部满足。
- 前端命令打印硬编码命中数量，没有断言数量必须为零。
- 种子检查匹配文本并统计，不证明三种角色全部存在，更不证明 changeset 在真实数据库中成功执行。

优化：Bash 包装启用并向嵌套 Bash 传递 errexit/pipefail，保留完整输出与真实退出码；增加 `--reject` 识别明确失败输出。多个正向条件重复传 `--expect`，数量/集合必须实际断言。静态检查、单元、构建和真实数据库验证分别说明。

工具不能识别任意命令的业务语义；echo OK、人为宽泛的正则、主动吞掉错误，仍需审查。

### P1：授予权限的上限与不同入口的授权关系缺失

证据：角色权限矩阵（历史来源：`ui.md:74`）、编辑与分配接口（历史来源：`design.md:154`）、普通创建/编辑写入 roleIds（历史来源：`design.md:195`）。

文档允许居委管理员新增、编辑和分配用户角色；单独分配接口使用 assign 权限，而普通 create/update 同时接受 roleIds，描述的唯一新增保护是最后超级管理员持有者检查。未明确谁可设置 is_admin、能否给自己或他人授予 super_admin、可授予角色集合，以及所有写入口是否执行同样的字段级授权。

优化：设计模板增加“操作者—动作/入口—目标与字段—可授予上限—后端拒绝条件—负向用例”表。对自授高权限、跨入口绕过 assign、越权改 is_admin 分别明确预期拒绝。业务规则未确定时返回澄清，不能代填。

这是设计契约缺口，需要另行校核业务实现，不能只凭文档断言已经发生提权。

### P2：页面范围从三个变成两个，未同步需求

证据：PRD 的三个新增页面（历史来源：`prd.md:155`）、页面验收（历史来源：`prd.md:169`）、UI 的两条新路由（历史来源：`ui.md:64`）、设计页面清单（历史来源：`design.md:241`）。

权限分配实际规划为角色页权限树与用户页弹窗，不是独立第三个新页面。合并能力可能合理，但旧 PRD 和 AC-07-5 仍要求三个新增页面。

优化：PRD 明确独立页面或嵌入位置，设计前核对页面/路由/接口/AC。改变交付形态时同步需求与原型并重新确认；不能凭设计阶段的实现选择覆盖已确认范围。

### P2：原型演示被扩大为真实界面行为证明

证据：UI 的无权限实测结论（历史来源：`ui.md:53`）、原型交互未测说明（历史来源：`ui.md:100`）、前端菜单设计（历史来源：`design.md:215`）。

原型声称菜单隐藏、直接 URL 无权限页和按钮显隐均已实测，但后续说明仅原型 JS 语法及静态渲染，没有端到端交互。直接 URL 授权也没有在技术设计中形成同等明确的路由门禁契约。

优化：五态表逐项记录测试对象（原型/实现）、角色、操作、预期、实际结果和证据。截图不证明保存、回显、真实 URL 或后端拒绝。原型验收与实现验收分别保留。

### P2：被确认的原型未绑定，截图依赖临时目录

证据：ui-scope（历史来源：`ui.md:5`）、原型与临时截图（历史来源：`ui.md:22`）。

原型 HTML 不在 ui-scope 中，所列的主要是实现文件和目录。UI 确认指纹只覆盖文档时，修改原型可能不会使确认失效。截图保存在 /tmp，当前存在也不能保证以后可回溯。

优化：使用 `prototypes` 声明已展示的原型与评审截图，持久保存在该 change 内；文件内容参与 UI 及后续确认/完成指纹。实现范围继续由 files/affected 声明，两者用途分开。

### P2：角色选择接口与用户分配权限可能不匹配

证据：居委管理员权限（历史来源：`ui.md:80`）、角色接口授权（历史来源：`design.md:158`）、角色下拉接口（历史来源：`design.md:175`）。

居委管理员有 user:assign，但没有 role:page；角色下拉接口被归入 system:role:*。若实现沿用该设计，允许分配的用户可能无法取得选项；全量返回所有角色也与可授予上限有关。

优化：明确受限可分配角色查询的授权、数据范围和使用入口；用同一操作者验证“查询选项→提交分配→再次回显”整条链路。

### P2：测试统计与证据层级不一致

证据：报告测试明细（历史来源：`test-report.md:33`）、实际回归证据（历史来源：`evidence/REQ-08-regression.json`）、设计测试策略（历史来源：`design.md:277`）。

报告将 DataPermissionSqlTest 记为 10 项，而已查看的回归日志该类统计为 3 项；总数相同不证明逐类明细正确。设计说明既有测试不依赖容器或数据库，报告却笼统称“单元/集成测试”。SQL 文本检查不能证明真实数据权限查询结果。

优化：按测试工具原始统计填写数量、方法与版本；对每条 AC 说明真实测试对象，避免把 unit/mock/static 标成 integration/e2e。

### P3：迁移编号与最终规范沉淀不够一致

证据：设计标题的 021～026（历史来源：`design.md:9`）、计划的 021～025（历史来源：`plan.md:11`）、Spec 处理（历史来源：`archive-report.md:40`）。

设计标题的迁移范围与实际计划/交付表不一致。没有已有 Spec 目录不等于不能建立首个正式能力规范；关闭全项目 specSyncRequired 会改变所有 change 使用的协议，而不只是本次归档。

优化：设计模板显式核对迁移编号、首次执行、重复执行、回滚与数据损失边界。优先建立首个规范；整个项目明确不采用 Spec 时再记录用户决定与全局配置，避免临时绕过检查。

## 3. 本次已落实到 t-flow 的改进

| 层 | 改进 | 可核对行为 |
|---|---|---|
| 运行时 | 逐 AC 覆盖、方法记录、未知 AC/重复 ID 检查 | REQ 全覆盖但遗漏 AC 时阻断 verify/archive；可选或未测用例不满足覆盖 |
| 运行时 | --reject、真实退出码/信号、Bash 严格执行与嵌套继承 | 管道内失败即使后续打印 PASS 仍为 failed；成功输出同时有失败文案可被拒绝 |
| 运行时 | prototypes 的目录/文件校验、指纹及证据绑定 | 原型须为本 change 内实际文件；修改后旧 UI 确认不能推进 |
| 模板 | PRD、design、UI、test-report、test-results、archive-report、evidence | 逐项填写 AC、测试层级、授权边界、范围差异、未测项与持久证据 |
| 阶段规则 | specify/design/plan/ui/verify/archive | 需求变更回退确认；原型与产品分开；未测不能包装成全部通过 |

旧 PRD 不声明 AC 时仍使用原 REQ 检查；旧 ui.md 不声明 prototypes 时保持兼容。更新后的模板和规则要求新产物填写这些信息。对有 43 条 AC 的本样本，新版会要求补足显式验收映射和测试方法，不会根据旧“8/8”结论自动背书。

5. 用户验收后再进行真正的归档。

这些业务工作未在本轮执行；本轮范围是优化 t-flow 的模板、规则、验收检查并提供审查报告。
